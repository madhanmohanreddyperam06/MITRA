# MITRA Authentication Documentation

## Overview

MITRA Phase 3 introduces a secure authentication and user management system built on JWT (JSON Web Tokens) and bcrypt password hashing. The system supports two user roles:

- **Admin**: Single administrator account with full user management privileges
- **User**: Regular users with access to chat and knowledge base features

## Architecture

```
Streamlit Frontend
        ↓
    JWT Token
        ↓
FastAPI API
        ↓
Authentication Layer (get_current_user, get_current_admin)
        ↓
AuthService (registration, authentication, JWT management)
        ↓
UserRepository (database operations)
        ↓
MySQL Database (users table)
```

## User Model

The `users` table contains the following fields:

| Field | Type | Description |
|-------|------|-------------|
| id | Integer | Primary key, auto-increment |
| username | String(50) | Unique, indexed, lowercase |
| email | String(255) | Unique, indexed, normalized to lowercase |
| password_hash | String(255) | Bcrypt hash (never plaintext) |
| full_name | String(255) | Optional display name |
| is_active | Boolean | Account status (default: True) |
| is_admin | Boolean | Admin flag (default: False) |
| created_at | DateTime | UTC timestamp of creation |
| updated_at | DateTime | UTC timestamp of last update |
| last_login_at | DateTime | UTC timestamp of last login |

## Password Security

### Hashing Algorithm
- **Algorithm**: Bcrypt (via passlib)
- **Work factor**: Default (12 rounds)
- **Salt**: Automatically generated by bcrypt

### Password Policy
- Minimum length: 8 characters
- Maximum length: 128 characters
- Cannot be empty
- No additional complexity requirements (avoid user frustration)

### Security Rules
- Passwords are never stored in plaintext
- Password hashes are never returned in API responses
- Passwords are never logged
- Password verification uses bcrypt's secure comparison

## JWT Authentication

### Token Configuration

Environment variables in `.env`:

```env
JWT_SECRET_KEY=CHANGE_ME_TO_A_SECURE_RANDOM_SECRET
JWT_ALGORITHM=HS256
ACCESS_TOKEN_EXPIRE_MINUTES=30
```

### Token Payload

JWT tokens contain minimal claims:

```json
{
  "sub": 123,           // User ID
  "exp": 1698765432,    // Expiration timestamp
  "iat": 1698763832     // Issued at timestamp
}
```

**Important**: Sensitive data (passwords, email, personal info) is never included in JWT tokens.

### Token Lifecycle

1. **Generation**: Created on successful login via `AuthService.create_access_token()`
2. **Validation**: Verified on each protected request via `AuthService.decode_token()`
3. **Expiration**: Tokens expire after 30 minutes (configurable)
4. **Storage**: Tokens are stored in Streamlit session state (client-side only)

### Token Security

- Tokens are stateless (no server-side storage)
- Invalid tokens are rejected with 401 Unauthorized
- Expired tokens are rejected with 401 Unauthorized
- Tokens should be sent in `Authorization: Bearer <token>` header
- Client-side logout simply discards the token

### Authentication Endpoints

#### Register User
```http
POST /api/auth/register
Content-Type: application/json

{
  "username": "newuser",
  "email": "user@example.com",
  "password": "SecurePassword123!",
  "full_name": "John Doe"
}
```

**Response (201 Created)**:
```json
{
  "id": 1,
  "username": "newuser",
  "email": "user@example.com",
  "full_name": "John Doe",
  "is_active": true,
  "is_admin": false,
  "created_at": "2024-01-01T00:00:00Z",
  "updated_at": "2024-01-01T00:00:00Z",
  "last_login_at": null
}
```

**Notes**:
- Public registration always creates normal users (never admin)
- Email is normalized to lowercase
- Username is normalized to lowercase
- `password_hash` is never returned

#### Login
```http
POST /api/auth/login
Content-Type: application/json

{
  "username_or_email": "newuser",
  "password": "SecurePassword123!"
}
```

**Response (200 OK)**:
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "bearer"
}
```

**Notes**:
- Accepts either username or email
- Updates `last_login_at` timestamp on success
- Returns generic error for invalid credentials (doesn't reveal if user exists)

#### Get Current User
```http
GET /api/auth/me
Authorization: Bearer <token>
```

**Response (200 OK)**:
```json
{
  "id": 1,
  "username": "newuser",
  "email": "user@example.com",
  "full_name": "John Doe",
  "is_active": true,
  "is_admin": false,
  "created_at": "2024-01-01T00:00:00Z",
  "updated_at": "2024-01-01T00:00:00Z",
  "last_login_at": "2024-01-01T01:00:00Z"
}
```

**Notes**:
- Requires valid JWT token
- Returns current authenticated user's information
- `password_hash` is never returned

## Streamlit Authentication Flow

### Login Flow

1. User opens Streamlit app
2. If not authenticated, login page is displayed
3. User enters username/email and password
4. Frontend calls `POST /api/auth/login`
5. Backend validates credentials and returns JWT token
6. Token is stored in `st.session_state.access_token`
7. `st.session_state.authenticated` is set to `True`
8. App redirects to main chat interface

### Authenticated API Calls

All API calls from Streamlit now include the JWT token:

```python
headers = {"Authorization": f"Bearer {st.session_state.access_token}"}
response = requests.post(url, json=payload, headers=headers)
```

### Logout Flow

1. User clicks "Logout" button in sidebar
2. Frontend removes `access_token` from session state
3. Frontend removes `authenticated` from session state
4. Frontend removes `current_user` from session state
5. App redirects to login page

**Note**: This is client-side logout only. The JWT token remains valid until it expires.

## Security Considerations

### JWT Secret Key

- **Never commit the JWT secret to version control**
- Use a strong, randomly generated secret (32+ characters)
- Use different secrets for development and production
- Rotate secrets periodically in production
- If a secret is compromised, all existing tokens become invalid
- **Production requires a secure secret** - the application will fail to start if not configured
- Development uses a fallback with a warning for convenience

### Password Security

- Passwords are hashed using bcrypt (not MD5, SHA1, or plain SHA256)
- Bcrypt automatically handles salting
- Password hashes are never logged or exposed in API responses
- Password policy enforces minimum length (8 characters)
- Maximum password length (128 characters) prevents DoS attacks

### Admin Protection

- **Exactly one admin account is supported**
- Public registration cannot create admin accounts
- Admin creation is restricted to the initialization script
- The script prevents duplicate admin creation
- Admin cannot delete or deactivate themselves (prevents lockout)
- Admin operations are protected by `get_current_admin` dependency

### Token Security

- Tokens expire after 30 minutes (configurable)
- Tokens are stateless (no server-side storage)
- Invalid/expired tokens return 401 Unauthorized
- Tokens are stored in client-side session state only
- Logout removes token from session state but doesn't invalidate server-side
- Tokens should be sent over HTTPS in production

### API Security

- Protected endpoints require valid JWT token
- Inactive users cannot authenticate even with valid token
- Admin endpoints check both authentication and authorization
- Generic error messages don't reveal if accounts exist
- Sensitive fields (password_hash) are never in API responses
- CORS is configuration-driven (not wildcard `*`)

### Database Security

- Email and username have unique constraints
- Admin operations use database transactions
- User deletion/activation checks admin count before execution
- Timestamps use UTC for consistency

## Troubleshooting

### Authentication Fails

**Problem**: Login returns 401 Unauthorized

**Solutions**:
1. Verify credentials are correct
2. Check if user account is active (`is_active = true`)
3. Verify JWT secret key matches between backend and config
4. Check database connection
5. Review logs for specific error messages

### Token Expired

**Problem**: API calls return 401 after some time

**Solution**: Tokens expire after 30 minutes. User must re-login.

### Admin Already Exists

**Problem**: `create_admin.py` refuses to create admin

**Solution**: This is expected behavior. Only one admin is allowed. If you need to reset admin credentials, contact support or directly modify the database (not recommended).

### Cannot Deactivate Admin

**Problem**: Trying to deactivate admin returns 400 error

**Solution**: This is a safety feature. You cannot deactivate the only admin account to prevent lockout.

### Streamlit Cannot Connect to Backend

**Problem**: Login fails with "Cannot connect to the backend"

**Solutions**:
1. Verify backend is running on http://localhost:8000
2. Check CORS configuration in `.env`
3. Verify `API_BASE_URL` in Streamlit components
4. Check firewall settings

### Migration Fails

**Problem**: `alembic upgrade head` fails

**Solutions**:
1. Verify MySQL is running
2. Check database credentials in `.env`
3. Ensure database exists
4. Review Alembic logs for specific errors

### Tests Fail

**Problem**: Authentication tests fail

**Solutions**:
1. Ensure test database is isolated from production
2. Check that test fixtures are properly configured
3. Verify all dependencies are installed
4. Run tests with `-v` flag for verbose output
